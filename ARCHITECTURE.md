# Architecture decisions — Lambruk Pantry on Horizon

A decision record for how `design/DESIGN-TOKENS.md` maps onto this Horizon build. Written after confirming Horizon uses one global colour **palette** (not per-section colour **schemes** — verified: no `"type": "color_scheme"` setting exists anywhere in `sections/`, `blocks/`, or `config/settings_schema.json`) and after reading `config/settings_schema.json`, `assets/base.css`, and the `snippets/` that actually emit Horizon's CSS custom properties.

This record exists so the reasoning survives past this session — each decision below states what we're doing, why, and what evidence from the theme source drove it. **No theme file has been changed as part of writing this record.** It is the plan; implementation is separate work.

---

## 1. Colour: palette + a single heading override + an explicit muted token

**Decision**
- `page_background_color` → `--paper` (`#FBFAF7`)
- `page_text_color` → `--text-body` (`#4A5478`)
- One CSS rule overrides `h1`–`h6` to `--text-strong` (`#131A3E`)
- `--text-muted` becomes our own explicit custom property (`#686D84`), not Horizon's derived opacity-fade
- `--color-border` gets overridden globally to our gold hairline, with a specific fix for product cards (see below)

**Why global foreground = body colour, not heading colour**
Horizon has exactly one foreground role. `body { color: var(--color-foreground) }` in `color-palette.liquid`, and nothing in `base.css` gives headings an independent colour — they simply inherit. Since body copy vastly outnumbers headings on every page, setting the global foreground to `--text-body` and overriding the minority (headings) is less code than the reverse.

```css
/* new stylesheet, loaded after Horizon's own CSS */
h1, h2, h3, h4, h5, h6 {
  color: var(--text-strong);
}
```

One rule. It rides on top of whatever `page_text_color` is set to without touching `color-palette.liquid`.

**Why `--text-muted` needs to be a real second colour, not Horizon's fade**
Horizon's "muted" text isn't a colour — it's `rgb(var(--color-foreground-rgb) / 0.6)` (`--opacity-muted-text: 0.6` in `theme-styles-variables.liquid`). If foreground is `#4A5478`, a 60%-opacity fade of it is **not guaranteed to equal our approved `#686D84`**, and it's mechanically translucent rather than solid — it'll shift with whatever sits behind it (a photo, a navy band), which our contrast-checked, solid `#686D84` was specifically chosen to avoid. So:

```css
:root {
  --text-muted: #686D84;
}
```
...used directly wherever our own components need muted text, instead of Horizon's `--color-foreground-muted`.

**What `--color-border` inheriting foreground actually does — checked, not assumed**
`--color-border: {{ settings.page_text_color }}` in `color-palette.liquid` — so once foreground is `#4A5478`, `--color-border` becomes that colour too. Grepping every consumer:

- `accordion-styles.liquid`, `header-drawer.liquid`, `buy-buttons-styles.liquid`, `template-giftcard.css`, `search-modal.liquid`, `predictive-search-styles.liquid` all use it **solid** — `border: 1px solid var(--color-border)`. With foreground at `#4A5478`, every one of these hairlines renders solid blue-grey, not our warm gold `#E3D6C5`.
- `divider.liquid` already supports a per-instance override (`settings.divider_color`, falling back to `--color-border`) — useful precedent for point 2 below.
- `product-grid.liquid:225` — the actual **product card border** — reads `rgb(var(--color-border-rgb) / var(--product-card-border-opacity))`. Grepped for `--product-card-border-width` and `--product-card-border-opacity` everywhere else in the theme: **they are defined nowhere.** An undefined custom property with no fallback makes the whole `border` declaration invalid at computed-value time, so **product cards currently render with no border at all** — not "the wrong colour," genuinely absent. This was a surprise; worth knowing before assuming the card border "just needs a colour fix."

**Decision from that finding:** override `--color-border` globally to `#E3D6C5` (fixes every solid-consumer above in one shot), and *separately* define `--product-card-border-width: 1px` and `--product-card-border-opacity: 1` in the new stylesheet to activate the currently-dormant product-card border feature. Two small additions, not a rewrite of `product-grid.liquid`.

**Implemented 2026-08-20.** Went in as one coordinated change — palette values, CSS additions, and the fixes below all ship together, since setting the palette without them breaks hairlines and leaves headings uncoloured.

- `page_background_color` → `--paper` `#FBFAF7`; `page_text_color` → `--text-body` `#4A5478`. Both already referenced `settings.color_palette.background`/`.foreground` in `settings_data.json`, so only `color_palette` itself needed new values.
- `color1`/`color2` weren't scoped by this section originally — traced their real consumers before setting them (see below). `color1` → `#131A3E` (`--text-strong`; its only consumer is `palette_input_text`). `color2` → `#E3D6C5`, matching `--color-border`, for its genuinely decorative consumers (`drawer_border_color`, `popover_border_color`, `product.json` divider ×2).
- **`color2`'s two remaining consumers needed a different value, not the palette's.** `palette_input_border` and `palette_variant_border` are interactive-component boundaries, and `#E3D6C5` measures 1.37:1 on paper — fails WCAG 1.4.11's 3:1 minimum badly (see `DESIGN-TOKENS.md` §1 for the full check across the gold scale). Per instruction, didn't compromise the shared palette to fix this — overrode both settings directly to `#A07037` (`--gold-600`, 4.13:1), independent of `color_palette.color2`. Found and fixed the same problem in two more places outside the palette mechanism entirely: `templates/password.json`'s `input_border_color` (same setting, different template) and `templates/cart.json`'s cart-page order-summary `background_color`, which was reading `color2` as a *background* — checked the design source's `CartDrawer.jsx` directly, which sets the drawer's own background to `var(--paper)`, not gold; `#E3D6C5` there would have been visibly wrong, not just under-contrast. Both corrected to literal values (`#A07037`, `#FBFAF7`) rather than a `color_palette` reference.
- Heading colour: added `h1, h2, h3, h4, h5, h6 { color: var(--text-strong); }` to `lambruk-tokens.css` — **bare tag selector only**, not widened to `.h1`–`.h6` classes as first considered. Reason: Horizon's generic `text` block never renders a real `<hN>` tag regardless of `type_preset` — it's always a `<div>`/`<p>` — so the bare selector only ever catches genuine semantic headings (blog article titles, drawer/modal headings, hidden a11y `<h1>`s), all safe to recolour navy. Every heading actually authored this build so far uses `type_preset: "custom"` (class `custom`, not `h1`–`h6`), so it needed an explicit `text_color: "#131A3E"` on the block instead — done for all five `media-with-content` headings. **Quote-panel's `.h3 text-display-3` div was the one place a class-based widening would have looked right and been wrong**: it already gets correct colour by inheriting a *locally scoped* `--color-foreground` from `contrast-override` (its own `background_color`/`text_color`/`accent_color` settings, independent of the global palette). A `.h3` class rule at `:root` scope would have matched that div directly and beaten the inherited value — repainting the quote navy-on-navy, invisible. Left untouched; confirmed no other component currently combines a Horizon `.h1`–`.h6` utility class with a `contrast-override`-scoped surface, so the bare-tag-only rule has no other gaps to close right now.
- **Footer text colour was a related gap, found while checking this — not in the original plan.** The footer's brand blurb, all three link-list columns, the copyright bar, the policy links, and the social icons had no explicit `text_color`/`icon_color`, so they inherited whatever the global foreground became. Checked contrast of the new `#4A5478` on the footer's navy `#131A3E` background: **~2.2:1**, far under AA. The design source (`Footer.jsx`) uses `--text-on-dark-muted` (`rgba(247,245,242,.72)`) for exactly this content. Set `text_color`/`icon_color` to the hex+alpha equivalent, `#F7F5F2B8`, on all six affected blocks in `sections/footer-group.json`. The three column headings (`#AE7A3C`) were already explicit and needed no change.
- `--color-border-rgb` also needed redefining alongside `--color-border` — `product-grid.liquid`'s card border reads it through `rgb(var(--color-border-rgb) / var(--product-card-border-opacity))`, a separate custom property from `--color-border` itself, set in `color-palette.liquid` from `page_text_color.rgb`. Set to `227, 214, 197` (the `#E3D6C5` channels), matching the existing comma-separated convention `color-palette.liquid` itself uses for `--color-foreground-rgb`/`--color-background-rgb`.

**Verified 2026-08-20 against the live theme (`shopify theme dev`, computed styles read in-browser, not `theme check`).** Confirmed correct: body background/text (`#FBFAF7`/`#4A5478`), `--color-border`/`--color-border-rgb` at `:root` (`#E3D6C5`/`227, 214, 197` — the `layout/theme.liquid` load-order fix above holds), the Cafe-intro heading (`rgb(19, 26, 62)` = `#131A3E`), all six footer text/icon colours (`rgba(247, 245, 242, 0.72)` on a confirmed navy `#131A3E` footer background), `--color-input-border` (`#A07037`), and the cart drawer (paper background, gold `#E3D6C5` border-left).

**One real gap found, not anticipated by the consumer trace above: native product-card borders are navy, not gold.** `sections/main-collection.liquid` calls `contrast-override` with only `background_color` (no `border_color`), so `contrast-override.liquid`'s smart-contrast branch picks `--palette-darkest` for the border instead of reading our global `--color-border` at all — an entirely separate mechanism from the direct consumers traced earlier (accordion, header-drawer, search-modal, etc.), which do read `--color-border` directly and are unaffected. `--palette-darkest` is computed by `color-palette.liquid` as the darkest of the four `color_palette` entries, which is now `color1` (`#131A3E`) — so product cards render a 1px navy border, confirmed via computed style (`rgb(19, 26, 62)`) on `.product-grid__item` on `/collections/all`. Not fixed: forcing gold here means either passing an explicit `border_color` into `main-collection.liquid` (a further core-file edit, needs sign-off) or repointing `--palette-darkest` globally, which would also change the smart-contrast text-colour fallback used elsewhere and risks a different regression. Navy is a legitimate, on-brand hairline on a paper card, just not what §1 specified — flagged for a decision rather than silently left or silently changed.

## 2. Surfaces: native `background_color` + `contrast-override`, not a CSS layer

**Decision:** every new theme block that needs a non-default surface (paper-2, navy, etc.) gets its own `background_color` block setting, defaulting to the correct surface hex, following the pattern already used by `blocks/_card.liquid` — not a blanket CSS class system we invent.

**The existing pattern, as found in `blocks/_card.liquid`:**
```liquid
{% liquid
  if block_settings.background_color != blank
    render 'contrast-override', background_color: block_settings.background_color, section_id: block.id
  endif
%}
<div class="card{% if block_settings.background_color != blank %} color-custom-{{ block.id }}{% endif %}">
```
```json
{ "type": "color", "id": "background_color", "label": "t:settings.background_color", "placeholder": "t:settings.default" }
```
`_card.liquid` leaves the setting blank by default (inherits the ambient page background) and only engages `contrast-override` — which auto-picks a readable text colour from the palette extremes — when a merchant explicitly sets one.

**Worked example — one block, before applying this broadly**

Our navy quote panels (`Promise.jsx` / `WhyLambruk.jsx` — `--surface-dark`, `--text-on-dark`, gold eyebrow) are the surface furthest from Horizon's light default, so they're the clearest test of the pattern. Two things differ deliberately from `_card.liquid`'s convention:

1. **We give the setting a real default**, not a blank placeholder — this block's identity *is* navy; a merchant clearing the field shouldn't silently fall back to white.
2. **We pass explicit `text_color`/`accent_color`, not just a background.** `contrast-override`'s own doc comment says it *skips smart contrast entirely* when `text_color` is provided — meaning Horizon already has a first-class path for "don't guess, use this exact colour," not just auto-contrast. We use it, because "readable" isn't the bar — matching our approved gold-on-navy pairing is.

```json
{
  "type": "color",
  "id": "background_color",
  "label": "t:settings.background_color",
  "default": "#131A3E"
},
{
  "type": "color",
  "id": "text_color",
  "label": "t:settings.text_color",
  "default": "#F7F5F2"
},
{
  "type": "color",
  "id": "accent_color",
  "label": "t:settings.accent_color",
  "default": "#C6A06C"
}
```

```liquid
{% liquid
  render 'contrast-override',
    background_color: block_settings.background_color,
    text_color: block_settings.text_color,
    border_color: block_settings.accent_color,
    section_id: block.id
%}
<div class="quote-panel color-custom-{{ block.id }}">
  <p class="quote-panel__eyebrow" style="color: {{ block_settings.accent_color }}">{{ block_settings.eyebrow }}</p>
  <p class="quote-panel__text">{{ block_settings.text }}</p>
</div>
```

A merchant gets a real colour picker per instance (on-brand default, override allowed), `contrast-override` still emits the standard `--color-foreground`/`--color-border` variables scoped to `.color-custom-{{ block.id }}` for any child markup that doesn't set its own colour explicitly, and none of it required a bespoke CSS class system. This is the pattern for `paper-2` band sections, the alt-paper category tiles, and any other non-default surface — each gets its own `background_color` (+ `text_color`/`accent_color` where the surface isn't just light-on-light) with our surface's hex as the default.

Once this one example is confirmed to look right in the editor, apply the same shape to the other surfaces before building further sections against it.

**Bug fixed 2026-08-20 — quote-panel rendered narrow with paper gaps either side, on a `section_width: "full-width"` custom section.** Two separate causes stacked:
1. `templates/index.json`'s `section_why_lambruk` wrapper was still `"section_width": "page-width"` — a plain oversight, corrected to `"full-width"`.
2. That alone wasn't enough. `quote-panel.liquid`'s outer div carried both the `color-custom-{{ block.id }}` background *and* `max-width: 46rem; margin-inline: auto` — so the navy paint only ever covered the readable-text column, not the section. Fixed by splitting into two elements: the outer div keeps the background/padding and now has no width constraint of its own; a new inner `.quote-panel__content` div carries the `max-width`/centering, wrapping just the eyebrow/quote/illustration.
3. Splitting the div wasn't enough either — verified live and the background was still shrinking to ~816px on a 1280px viewport. Root cause: `section.liquid`'s flex wrapper (`layout-panel-flex--column`) uses `align-items: flex-start` when a section's `horizontal_alignment_flex_direction_column` setting is unset (as ours was), not `stretch` — a block without its own `width: fill` mechanism shrinks to its content's natural width instead of spanning the container. `quote-panel.liquid`'s schema has no `width` setting at all (unlike `group`, which does), so there was nothing to opt into fill with. Fixed by adding `width: 100%` directly to the outer div's inline style — a deliberate, block-specific choice, not a general pattern: this block is always meant as a full-bleed colour band, so hardcoding full width is correct here in a way it wouldn't be for a block meant to size to content.

Verified live at each step, not assumed from the diff — each of the three causes looked like "the" fix until measured, and stacking them was the only way to confirm nothing else was still constraining it. Worth checking any other full-width custom section that uses a block without its own `width` setting for the same shrink-to-content problem.

## 3. Accept Horizon's values where close

Three deliberate concessions, recorded with reasoning in `design/DESIGN-TOKENS.md` at their respective sections (§2, §8, §9) as well as here:

| Ours | Horizon's | Gap | Accepted because |
|---|---|---|---|
| 720px breakpoint | **750px** (`base.css`, hardcoded) | 30px | Imperceptible in practice; matching it would mean editing Horizon's own CSS for zero visible gain. |
| 20px mobile gutter | **16px** (`--page-margin` below 750px, hardcoded) | 4px | Below the threshold most people notice in a side margin; it's the one mobile spacing value Horizon ships for free — overriding it means touching `base.css` directly for a 4px difference. |
| Display 5 · Card at 26px | **24px** (`type_size_h5` nearest fixed option) | 2px | Not visually distinguishable on a card-caption-scale heading; every step expressible as a plain setting is one less custom rule to carry across future Horizon updates. |

The common thread: each gap is small enough to be invisible or near-invisible, and closing it would require editing a Horizon-owned file (`base.css`) rather than adding to ours. Per the customisation hierarchy in `CLAUDE.md`, that's exactly the trade the hierarchy asks us to make — settings and CSS additions first, Horizon's own files last resort, and these three don't clear the bar for "last resort."

**Not a template for every gap.** The 200px difference between our `--container` (1240px) and Horizon's nearest `page_width` option (`narrow` = 1440px) is *not* being accepted the same way — see §5.

## 4. Motion: our own tokens, scoped to our own components — Horizon's spring system untouched

**Decision:** do not override `--hover-transition-duration`, `--ease-out-quad`, `--ease-out-cubic`, or any `--spring-d*-b0-duration` variable. Define our own timing tokens and apply them only inside CSS we write for our own blocks/sections.

```css
:root {
  --lambruk-dur-fast: 140ms;
  --lambruk-dur-base: 240ms;
  --lambruk-dur-slow: 420ms;
  --lambruk-ease-out: cubic-bezier(.22, .61, .36, 1);
}

/* used only within our own component selectors, e.g.: */
.quote-panel__eyebrow { transition: color var(--lambruk-dur-fast) var(--lambruk-ease-out); }
```

**Why not just override Horizon's variables globally:** Horizon's animation system is partly spring-physics-based — `--spring-d220-b0-duration` etc. name a duration *and* a bounce coefficient as a matched pair, tuned for specific motion curves. Swapping the duration alone (via a blanket variable override) would desync it from the bounce it was tuned against, producing motion that's neither our calm/editorial curve nor Horizon's intended spring — worse than either. Our components get our exact motion; Horizon's own interactions (drawers, quick-add, page transitions) keep behaving as Horizon intended.

## 5. Everything else: one new stylesheet, layered over Horizon — never edits to Horizon's files

Every remaining Category 3 item from the settings-mapping review becomes a CSS custom property in a **single new asset** (`assets/lambruk-tokens.css`), loaded after Horizon's own CSS. One file, with clearly marked TOKENS and UTILITIES sections rather than splitting custom properties and classes across two assets, to avoid a second global request. Nothing here edits `base.css` or any other Horizon-owned snippet other than the two lines noted in "Upgrade-tracked modifications" below.

**Correction, 2026-08-20 — the stylesheet had to move from `snippets/stylesheets.liquid` to `layout/theme.liquid`.** The original plan (loading it there, right after `base.css`) works for tokens Horizon never touches again, but not for `--color-border`: `color-palette.liquid` sets that same custom property from `page_text_color`, and it's rendered *after* `stylesheets` in `layout/theme.liquid` (`{%- render 'stylesheets' -%}` then, four lines later, `{%- render 'color-palette' -%}`). Same specificity (`:root` in both), later source wins — our override would have been silently overwritten back to whatever `page_text_color` resolves to, with no error. Moved the `stylesheet_tag` line itself to `layout/theme.liquid`, directly after `{%- render 'color-palette' -%}`, so it loads last and actually wins. This does not affect scoped surfaces like quote-panel's `contrast-override` — those set `--color-border` on a class selector rendered even later, deep in `<body>`, which still naturally wins over both.

Confirmed contents so far:

- `--text-muted: #686D84` (§1)
- `--color-border` override to `#E3D6C5`, plus `--product-card-border-width`/`--product-card-border-opacity` to activate the dormant card border (§1)
- `--lambruk-dur-fast/base/slow`, `--lambruk-ease-out` (§4)
- `--section-y: 96px`, `--measure-prose: 820px` — no Horizon setting exists for either; theme-level, not per-block, since Horizon's own vertical rhythm is controlled per-section rather than globally

- `--shadow-whisper`, `--shadow-card`, `--shadow-lift` — no product/content-card shadow setting exists in Horizon at all (only `card_hover_effect`, a transform, and drawer/popover shadows elsewhere); these become pure CSS, applied via our own card component styles
- `--icon-accent: #8A6A32` (recorded in the now-archived `design/_archive/Lambruk Pantry Design System/tokens/colors.css` and reconfirmed against `design/design_handoff_website/` on 2026-08-20 — needs the equivalent added to the theme's own new stylesheet when icons are built)

  **Two real bugs found during verification, both pre-existing, not introduced by this change:**
  1. **Font-size was silently pinned to 32px on every viewport, including desktop — affecting the plain `quote` path too, not just the new segmented one.** The block's quote text carries both `.h3` (Horizon's own utility, `assets/base.css`) and `.text-display-3` (this project's fluid-clamp token). Horizon's own rule targets `.h3.h3` — two class selectors, specificity (0,2,0) — while `.text-display-3` is a single class, (0,1,0). Horizon's flat `--font-h3--size` (`2rem` = 32px, no viewport interpolation) was winning regardless of the intended fluid `--display-3-size` clamp(32px, …, 40px), on specificity alone, at every viewport including desktop. Confirmed live before the fix: computed `font-size: 32px` at a 1280px viewport, where the clamp should resolve to 40px. Font-size itself was *not* changed from the already-reviewed `--display-3-size` token (`DESIGN-TOKENS.md` §2 already documents 44/30 raw values deliberately absorbed into this step) — only line-height is overridden per-instance in `quote-panel.liquid` now, since Display 3's own 1.08 line-height is right for a short heading but wrong for this quote's wrapping, multi-line sentence, which the source gives 1.45 desktop / 1.5 mobile instead. Where the specificity fix itself lives moved during the follow-up below — see that entry for the current state.
  2. **Inline illustrations had no `vertical-align`, defaulting to `baseline`** — sat low relative to the surrounding text instead of visually centred on it. Design specifies `vertical-align: middle` explicitly on all three images, both breakpoints. Added to the shared `.quote-panel__illustration` rule (harmless for the legacy trailing-illustration usage, which has no other inline content on its own line to align against).

  **Verified live** on 182395437357, desktop and mobile, via computed styles: font-size 40px desktop / 32px mobile (32 vs. the source's raw 30 is the same already-approved Display 3 consolidation, not a new gap); line-height 58px desktop (40 × 1.45) / 48px mobile (32 × 1.5) — both exact; icon height 76px desktop / 52px mobile; `vertical-align: middle` on all three; margins 14px/14px (illustration 1), 14px/6px (illustrations 2 and 3) desktop, uniform 6px all three mobile; container 1000px; no comma after "fruit," no trailing full stop; centred text with the two-line break landing exactly where the source's `<br>` puts it. Screenshotted both breakpoints against the design side by side — visually matching.

  **Follow-up, same day — checked whether the `.hN.hN` collision is general, then moved the fix to the token layer.** Asked (and answered with live computed styles, not just reasoning from the CSS) whether the same collision hits `.text-display-1/2/4/5` or any `.text-1/2/3` utility anywhere they're combined with a Horizon `.hN` class. It doesn't, today: `grep`ing the whole theme found `.text-display-1/2/5` and `.text-1/2/3` don't exist as CSS classes anywhere — every other use of those scale steps is a direct inline `style="font-size: var(--display-N-size)"` on the individual component, which is immune to this collision regardless (inline styles beat any class-based specificity trick). `.text-display-3` was the only class with a live collision, in exactly the two lines just fixed above. `.text-display-4` was defined in `assets/lambruk-tokens.css` but, per the same audit, applied as a class nowhere in the theme — its own `--display-4-size`/`--display-4-line-height` tokens are very much alive (8 live consumers: `templates/index.json` ×3, `templates/product.json` ×4, `templates/page.cafe.json`, plus two of this session's own scoped success-state stylesheets), every one of them via the same inline-style pattern, never via the class.

  The underlying *mechanism*, though, is general: `assets/base.css` defines all six Horizon heading rules the same way, `.h1.h1` through `.h6.h6`, each pairing two class selectors with a flat non-fluid `--font-hN--size`. ## 7. Verification gap: `theme check` doesn't validate JSON against a section's own schema

Found 2026-08-20 when three edits to `sections/header-group.json`, `sections/footer-group.json`, and `templates/404.json` all passed `shopify theme check` clean, then were rejected outright on real upload to theme `182395437357` (surfaced via the local preview at `127.0.0.1:9292`, then reproduced independently against a second `shopify theme dev` session):

- `footer_utilities_jLGE8U` had 4 blocks against `footer-utilities.liquid`'s declared `"max_blocks": 3`.
- `header-group.json`'s `"order"` array referenced a section id no longer present in `"sections"` — a leftover from a prior edit.
- `templates/404.json` set `padding-block-start`/`padding-block-end` past `main-404.liquid`'s declared range `max: 100`.
- Two more of the same shape, only visible after re-verifying against the live theme rather than trusting a clean sync log: `divider_color`/`background_color_top` used `rgba(…, .28)` / `rgba(…, .92)` — Shopify's colour-setting validator rejects a decimal with no leading zero (`0.28`, not `.28`), even though it's valid CSS a browser parses fine.

**Why `theme check` missed all five.** Checked its rule list (`shopify theme check --list`) — the closest candidates are `ValidSchema`, `ValidSettingsKey`, and `JSONMissingBlock`. What they actually validate: that a section's *own* `{% schema %}` block is syntactically well-formed, that setting IDs referenced in Liquid exist in that schema, and that a JSON template's block *types* are valid. None of them cross-reference **instance data** in a template or section-group JSON file (`sections/header-group.json`, `sections/footer-group.json`, `templates/404.json`, `config/settings_data.json`) against the *runtime constraints* declared in the section/block schema it's instantiating — `max_blocks`, a setting's `min`/`max` range, or platform-level value-format rules like valid CSS colour syntax. `theme check` lints Liquid and JSON *structure*; it doesn't simulate what Shopify's own admin-side schema validator does when a theme is actually synced. That validator is authoritative for this whole error class, and nothing local reproduces it.

**The check that would have caught it: an actual sync.** `shopify theme dev --theme 182395437357` (or `theme push` to the same, unpublished, theme) performs the real server-side validation on every file it uploads — that's literally how these five were found. There is no local, offline equivalent; the checks that matter here only exist on Shopify's side.

**Practice change.** `shopify theme check` remains necessary (it catches things a live sync doesn't — translations, deprecated tags, accessibility) but is no longer sufficient on its own for changes to section-group JSON (`header-group.json`, `footer-group.json`), template JSON, or any settings touching schema-declared ranges/max_blocks/colour values. Those changes need a real sync — `shopify theme dev` running, or a one-off `theme push` — checked for upload errors before considering the change done, not just a clean `theme check` run. Worth folding into the `/qa` skill and `workflow/PIPELINE.md` directly rather than relying on this note being remembered per-session.

## 8. `.theme-check.yml`: `MatchingTranslations` disabled deliberately

Lambruk Pantry is English-only. ## 9. Design-system type on generic blocks: `font_size: var(--display-N-size)`

Every section built from Horizon's generic `text` block (the composable pattern §5 and the media-with-content work both lean on) needs headings sized to our canonical scale, not Horizon's own `type_size_h1`–`h6` settings — those are a different, uncoordinated scale (see quote-panel's original h3 problem: flat 32px, no fluid step, because Horizon's own fluid algorithm only activates above a 48px cutoff). Rather than solve this per-section, or build a bespoke block every time a heading needs correct sizing, the fix is one setting value.

**The technique:** on a `text` block, set `type_preset: "custom"` and `font_size: "var(--display-N-size)"` (or any raw CSS value, including a literal `clamp(...)` string) instead of one of the schema's enumerated px options.

**Why this works, confirmed empirically, not just by reading the code — this session already had two cases where static reasoning missed a real server-side validation rule (`max_blocks` type allowlist, the `rgba()` leading-zero requirement), so this was tested against a live sync before relying on it:**
- `font_size` is declared as a `select` in `text.liquid`'s schema, with a fixed list of px options — but that only constrains the theme-editor's dropdown UI. Confirmed the platform's schema validator does **not** reject a value outside that list when set directly in JSON, unlike `range`/`color`/`url` settings (both of which we've hit real rejections on this session).
- `snippets/typography-style.liquid` tries to parse `settings.font_size` as a bare rem number (`split: 'rem' | first | times: 1.0`) to decide whether to build its own clamp. That parse fails silently on a non-numeric string like `"var(--display-3-size)"`, evaluates to `0`, falls under the fluid cutoff, and hits the plain `else` branch — which just echoes the raw setting value into `--font-size:` verbatim. A test block set this way and synced to the live theme measured **40px at desktop, 32px at mobile (375px)** — genuinely fluid, not a coincidence at one viewport.

**The caveat: `line-height` does not get the same free ride, and this is deliberate, not an oversight to fix reflexively.** Unlike `font_size`'s passthrough, `typography-style.liquid` builds `--line-height` by *string-interpolating* your selection into a fixed variable name — `--line-height--{type}-{tight|normal|loose}` — never a raw echo. `type` here is inferred from the same (failed) font-size parse, defaulting to `body`, so a heading set this way gets `--line-height--body-normal` (1.4) rather than Display 3's actual 1.08. Visually looser than intended on any heading that wraps to multiple lines; a non-issue on ones that don't. Left unsolved deliberately on the five `media-with-content` headings (2026-08-20) — pending a look at the real preview, since which headings wrap and which don't determines whether this is even worth solving, not something to fix pre-emptively.

**Adopt this as the standard.** Any generic `text` block needing correct heading size going forward should use `font_size: var(--display-N-size)` rather than Horizon's native presets or a fixed px value — solved once, here, rather than re-decided per section.

## 13. Wholesale page — finished in one pass, all five sections

Audited against the full design source, 2026-08-20: five sections exist in the design, in order — Hero, Wholesale Benefits, Traceable to the grower, Who we supply / Packaging Formats, Partnership Enquiry. Only two were built (Benefits and Traceable), and in the wrong relative order (Traceable was first, Benefits second — reversed from the source). **Structure** — every new section is the same native `section` + `group` + `text`/`button`/`icon` composition already established (§10–§12), no new blocks except the enquiry form (below). One new technique: Horizon's generic `section` has no per-side border setting (all-sides only, like `group`), so the design's `border-top`/`border-bottom` hairlines between sections are built with a standalone `_divider` block placed first (for a top border) or last (for a bottom border) in the section's own block list, rather than faked with the section's own border setting, which would add unwanted side borders too.

**The Hero's "Submit Enquiry Form" button needed a real anchor to the enquiry section, and neither obvious way to give it one works.** Checked first: an `id` attribute in a richtext `text` setting — rejected outright by the platform (`Attribute 'id="..."' is not permitted on tag '<p>'`), confirmed by a real upload attempt, not assumed. No block in this theme has a custom-anchor/CSS-id setting either. The only real anchor available is Shopify's own auto-generated section wrapper id (`shopify-section-{template_id}__{section_key}`), read directly from the live DOM: `shopify-section-template--25873630921005__wholesale_enquiry`. The button's `link` is hardcoded to `#shopify-section-template--25873630921005__wholesale_enquiry` — the numeric prefix is the specific template's own stable id (doesn't change on ordinary edits, only if the template were deleted and recreated), but it's still a hardcoded value with no platform guarantee, not something derived at render time. **If this link ever stops scrolling to the right place, re-check the enquiry section's actual rendered id and update the hero button's `link` setting to match.**

**New token**: `--display-1-size` (`clamp(38px, 29.741px + 2.118vw, 56px)`, DESIGN-TOKENS.md §2) for the Hero heading — the first heading this build needed at Display 1 · Hero scale. Note: `type_size_h1` in `config/settings_data.json` already happens to be `56`, matching the target exactly, and might be fluid natively (Horizon's fluid cutoff is 48px, and 56 clears it) — used the custom token anyway rather than the native `h1` preset, for the same reason every other heading this build does: headings are authored `type_preset: "custom"` so `text_color` reaches them (the CLAUDE.md rule), and reaching for a native preset here would be the one heading in the whole build that doesn't follow that pattern.

**New block: `blocks/lambruk-wholesale-enquiry-form.liquid`.** The design's enquiry form has six required fields (business name, contact name, email, phone, business type, location) plus a multi-select "interested in" and a message textarea — Horizon's native `contact-form.liquid` only has `name`/`email`/`phone`/`body`, no split business/contact name, no business type or location, nothing for a multi-select. Built by extending the same pattern `contact-form.liquid` itself uses — `{% form 'contact', id: form_id %}`, the `contact[id]` hidden field, `form.errors`/`form.posted_successfully?` for state — with the extra fields added as their own `contact[Field Name]` inputs. Shopify's contact form forwards any `contact[...]` key into the notification email natively, so this is additive to the native mechanism, not a rebuild of it. "Interested in" is a plain checkbox list (`contact[Interested in][]`), not the design's pill/tag picker — the user's call, made deliberately for the accessibility win, not a fallback. Success state replaces the form fields entirely with the design's exact confirmation copy, rather than native `contact-form.liquid`'s behaviour of showing the success message above the still-visible form.

**Open item, not a theme decision — see `CLAUDE.md`.** The native contact form sends to one address, set globally in Admin (Settings → Notifications). Wholesale enquiries and general customer service currently land in the same inbox unless that's addressed before go-live — flagged there, not fixed here, since there's no theme-side lever for it.

**Known gap:** the Partnership Enquiry section's award callout (Bronze Medal, Melbourne Royal 2024) has no image — same photography dependency already tracked in Open Questions above, not pointed at a placeholder or invented substitute.

**Attempted to verify a real submission live; couldn't complete it — and this time pinned down exactly why, not just "an automated-testing limitation."** Filled and submitted the form repeatedly — JS `.click()`, `form.requestSubmit()`, a genuine OS-level mouse click on the real button (confirmed landing correctly via `elementFromPoint`), on both the local dev proxy and the real `preview_theme_id` Shopify domain. None produced a `/contact` POST in the network log. Ran a control test first: Horizon's own **unmodified native** contact form (`templates/page.contact.json`) fails identically under the same conditions, which rules out the block itself. Then went one step further and bypassed the browser entirely — POSTed directly to `/contact` with `curl`, replicating the exact form fields, using a real preview session cookie. **Got a `403` back: Cloudflare's own "Verifying your connection" managed challenge**, sitting in front of the whole store. That's the actual, confirmed cause — automated, non-browser-fingerprinted POSTs to `/contact` are challenged before they ever reach Shopify's backend. Real human visitors in a real browser aren't affected by this; it's the same protection any Shopify store has. **Still needs one real, human-driven submission to see the live error/success states firsthand** — I've now confirmed why I can't get there myself, not just that I couldn't.

**Bug found this way, fixed 2026-08-20 — the error state showed an icon with no message text.** Root cause: the block's error markup was copied verbatim from `blocks/contact-form.liquid`, which hardcodes `form.errors.messages.email` — the *only* field Horizon's native 4-field form ever needs to report on. This form has six required fields; if the actual failing field is anything other than email, `form.errors` is truthy (icon renders) but the hardcoded `.email` lookup comes back blank (no text) — exactly the symptom reported. Horizon has the correct, general pattern elsewhere in the same theme (`snippets/blog-comment-form.liquid`): iterate `{% for field in form.errors %}`, reading `form.errors.translated_fields[field]` + `form.errors.messages[field]` per field, so every erroring field gets named, not just one. Rebuilt the error block on that pattern instead — added `role="alert"` for screen readers (also missing before), a visible heading ("We couldn't send your enquiry — please fix the following:"), a list item per erroring field, and `aria-invalid`/`aria-describedby` wired to each of the four Shopify-recognized fields (`name`/`email`/`phone`/`body` — the only ones Shopify's contact form validates server-side; the custom fields like Business name have no server-side validation to report on, only the client-side `required` attribute). Colour uses Horizon's existing `--color-error` token rather than a new one.

**Two more bugs, both only surfaceable by a real human submission (Cloudflare blocks automated ones — see above) — reported 2026-08-20, fixed the same session.**

1. **Blocking: the form could not be submitted at all.** `contact[Interested in][]` — array-style field naming for the checkbox group — got rejected server-side with "Interested in is invalid." Shopify's contact form endpoint expects a flat hash of string values per field; sending an array for one key breaks its validation rather than being silently accepted or ignored. No other field in this theme uses array-style naming, so nothing else was at risk of the same bug. Fixed by dropping the checkboxes' `name` attribute entirely (pure UI, nothing submitted for them directly) and adding one hidden `contact[Interested in]` field that a small inline script populates with the checked values joined into a single comma-separated string on submit — a single string field, which is what the endpoint actually accepts.

2. **Severe UX: every field was wiped after a rejected submission.** Shopify's `form` object only echoes back the four fields it natively recognizes — `form.name`/`form.email`/`form.phone`/`form.body` — confirmed against Shopify's own Liquid docs and this theme's native `contact-form.liquid`, which relies on exactly those four and nothing else. There is no server-side echo for arbitrary `contact[...]` fields, so the three custom fields (Business name, Business type, Location) and the interests checkboxes had no way to survive the redirect-back-with-errors round trip — confirmed by checking whether Shopify's `form` drop exposes anything more general than the four named accessors; it doesn't. Fixed two ways: (a) the four native fields now set `value="{{ form.xxx }}"` on the input, the same echo mechanism `contact-form.liquid` already relies on, just missing from this block before; (b) the three custom fields and the interests checkboxes are cached to `sessionStorage` (keyed to the block's own id, so multiple instances never collide) on every submit attempt, and restored from there when the page re-renders with `form.errors` present, then cleared once `form.posted_successfully?` is true. Client-side only, scoped to this one block — not a new site-wide form-handling pattern.

**What I could verify myself vs. what still needs the real submission you're about to do.** Cloudflare's challenge (see above) means I still can't get a real `form.errors` response server-side — so I directly exercised the client-side logic instead, which is fully testable without a server round trip: filled the form, dispatched the `submit` event, and confirmed the hidden `contact[Interested in]` field joined to `"Tea range, Relishes & chutneys"` (a single string, not an array) and that `sessionStorage` captured the three custom fields plus both checked interests in the expected shape. Then cleared the visible fields and ran the exact restore branch from the block against that cached data — all three custom fields and both checkboxes came back correctly. That confirms both fixes' logic is correct. What it can't confirm: that Shopify's backend actually *accepts* the joined string (theory-based on the "is invalid" error being array-vs-string, not empirically re-tested against the real endpoint), and that the real `form.errors`-present page render triggers the restore branch the same way my manual simulation did. **Success-state centering bug — found 2026-08-20, fixed same session.** Reported after a real submission: the success state's content sat slightly left of centre inside the card rather than centred, with the explicit instruction to check rather than assume and verify with computed positions, not by eye. ## 14. Text 1 / Text 2 body-copy layer — a gap identified at the start of the build, never closed until now

**This sat unbuilt for the whole project.** The original Horizon settings mapping identified early on that body copy needed a two-step split — Text 1 · Large (16–17px fluid) and Text 2 · Body (fixed 15px) — because Horizon has exactly one native paragraph preset (`type_size_paragraph`, a five-value select: 10/12/14/16/18px, no 15 or 17 option anywhere in it) and the design's actual body-copy sizes don't land on any of those five values. The layer needed to reach those two in-between steps was never actually written. `type_size_paragraph` sat on Horizon's untouched stock default, `"14"` (`config/settings_data.json`), for the entire build up to this point. Confirmed by grepping `ARCHITECTURE.md` and `lambruk-tokens.css` for any prior trace of it before starting this pass — zero hits; it wasn't even logged as a known gap, just silently absent. Every `text` block across every page that used `type_preset: "rte"` or `"paragraph"` without its own `font_size` override — the default way to author body copy — was rendering at 14px instead of 15–17px, discovered 2026-08-20 while investigating a Wholesale-page spacing complaint that turned out to trace back to this.

**The fix, following §9's established technique.** Two new tokens in `assets/lambruk-tokens.css`:
- `--text-1-size: clamp(16px, 15.541px + 0.118vw, 17px)` (DESIGN-TOKENS.md §2's Text 1 · Large, recomputed independently from the 390→1240px viewport range rather than trusted from the doc — matches)
- `--text-2-size: 15px` (Text 2 · Body, fixed, no interpolation, per the same source)

Applied via the same passthrough §9 already proved: `type_preset: "custom"` + `font_size: "var(--text-1-size)"` or `"var(--text-2-size)"`, which `typography-style.liquid` echoes verbatim into `--font-size` on its failed-rem-parse fallback path. Line-height doesn't get that same free ride (§9's own caveat) — but for body-scale text the caveat is actually harmless: the `type` variable both `text.liquid` and `typography-style.liquid` compute from a failed parse defaults to `'body'` regardless, which is already the correct bucket here (unlike a heading passed through the same mechanism, which would incorrectly land in `'body'` too). `line_height: "loose"` was set on every instance — `--line-height--body-loose` is `1.6` (`theme-styles-variables.liquid`), an exact match for Text 2 and close enough to Text 1's 1.65 target (0.05 off) that a new token wasn't worth adding for line-height alone.

**Per-instance size decisions were checked against the design source, not assumed from the step name.** For every block, the actual raw `font-size` in `design_handoff_website/LambrukPantry Desktop.dc.html` was grepped and matched against DESIGN-TOKENS.md §2's "raw sizes absorbed" table (raw desktop 17/18/19 → Text 1; raw desktop 15/16 → Text 2) rather than guessed from context. ## 15. Eyebrow tracking — the second specified-but-never-built gap found this pass, plus the hero max-width follow-up

**Reported 2026-08-20, initially as a correction to an earlier (wrong) description of the bug** — the user had the direction backwards in a first pass (thought our tracking was wider than the design's); asked to verify from source rather than take the correction at face value, per the project's standing rule. **Root cause, same closed-enum mechanism as `max_width`, not `font_size`'s free passthrough.** `letter_spacing` on a `text` block is a three-value select (`tight`/`normal`/`loose`), string-interpolated into `--letter-spacing--{type}-{value}`. Checked every value Horizon defines for all three types (display/heading/body) in `theme-styles-variables.liquid` — none exceed `0.03em` ("loose"). 0.22em was never reachable through any native option, and no eyebrow-specific token existed anywhere in `lambruk-tokens.css` before this (grepped for it — zero hits). **Fixed with a new named token, `--letter-spacing--body-eyebrow: 0.22em`, not by redefining the existing `loose` step.** Redefining `--letter-spacing--body-loose` directly was ruled out: the Text 1/Text 2 body-copy blocks from §14 also use `line_height: "loose"` (a *different* variable, `--line-height--body-loose`, unaffected by this), but if any future body-copy block ever needed loose *tracking* too, redefining the shared step would leak this eyebrow-specific value into unrelated content. `letter_spacing: "eyebrow"` — an off-enum value, same technique as `max_width: "wide"` in §14 — applied to all 17 real eyebrow instances found sitewide (see table below). Every eyebrow computes `type: "body"` in `typography-style.liquid`'s own parse (`0.75rem` → `0.75`, under every display/heading cutoff), so only the body-scoped token was needed.

## 17. Full audit — every proposal in this file and DESIGN-TOKENS.md checked against what's actually in the theme

**Requested 2026-08-20, after the eyebrow-tracking gap (§15) turned up the same way Root Cause 1 did (§14) — the user wanted to know if there were more.** Method: read every documented decision in this file and in `design/DESIGN-TOKENS.md` (the "original Horizon mapping"), then check each one's actual consumer(s) live or in the JSON/CSS source, rather than trusting the doc's own account of its status. **Finding 1 — the Product page's own title (not the card title) was never given the Display-scale treatment at all, and it's visibly wrong.** Checked every heading role on the site against the canonical type scale; the main Product Detail Page heading — literally `<h1>{{ closest.product.title }}</h1>` in `product.json` — turned out to be byte-identical to Horizon's pristine baseline (confirmed via `git show b2d7c4b:templates/product.json`, zero diff): `type_preset: "h3"`, an inert `font_size: "1rem"` left over from Horizon's own default JSON that has no effect (non-`"custom"` presets don't read `font_size` at all — `typography-style.liquid`'s whole capture block is gated on `preset == 'custom'`). **Finding 2 — a second, distinct bug on the same headings: colour, not just size, on every page using a *native* (non-`"custom"`) heading preset without an explicit `text_color`.** The existing rule in this file (`CLAUDE.md`, restated §1: "heading `text` blocks need an explicit `text_color`... without it, it silently inherits body-text colour") was reasoned through and verified only for `type_preset: "custom"` headings — "every heading actually authored this build so far uses `type_preset: custom`" (§1, written 2026-08-20, true *at the time*). This sweep found the rule doesn't cover *native*-preset headings (`h1`–`h6`) the same way, and several exist, unnoticed until now:

| Page | Heading | Preset | Colour rendered |
|---|---|---|---|
| Product (`product.json`) | `{{ closest.product.title }}` | `h3` | `rgb(74, 84, 120)` — body grey, not navy |
| Product (`product.json`) | "You may also like" | `h4` | Same mechanism, `text_color: ""` |
| Collection (`collection.json`/`.all.json`, every collection) | `{{ closest.collection.title }}` | `h2` | `rgb(74, 84, 120)` — confirmed live on `/collections/all`, font-size a coincidentally-correct 48px, colour still wrong |
| 404 (`404.json`) | "This page has left the shelf" | `h1` | `rgb(74, 84, 120)` — confirmed live, font-size a coincidentally-correct 56px |

**Root cause, traced to a specific, higher-specificity Horizon rule the bare `h1`–`h6` override in `lambruk-tokens.css` doesn't reach.** `assets/base.css:647-659` defines `h1, .h1.h1, .text-block.h1 > *, .text-block.h1 :is(h1, h2, h3, h4, h5, h6) { ...; color: var(--color); }` — a *combined* selector where the last branch (`.text-block.h1 :is(h1...)`) has specificity (0,2,1), well above `lambruk-tokens.css`'s bare `h1 { color: var(--text-strong); }` (0,0,1). `--color` is only ever set inline when the block's own `text_color` setting is non-blank (`text.liquid`'s style capture); when it's blank, `color: var(--color)` is invalid at computed-value time, and for an inherited property like `color` that means falling through to the parent `.text-block`'s own computed colour — which resolves through the *same* pattern (`color: var(--color, var(--color-foreground))`) down to `--color-foreground`, the global body-text colour. Confirmed this is specifically the *native-preset* path, not the `custom`-preset one already covered: a `custom`-preset heading has no competing `.text-block.h1 :is(...)`-shaped rule (its class is `custom`, not `h1`–`h6`), so the bare tag-selector override is the only rule touching it and wins outright — exactly why the existing §1 reasoning held for every heading built so far, and exactly why it stopped holding the moment a *native*-preset heading showed up.

**Not fixed in this pass — reporting only, per the audit's own scope.** The fix is mechanical once known (either add `text_color` to each of these four blocks, matching the existing convention, or add a lower-effort blanket rule — worth deciding which, since a blanket fix here risks the same kind of quiet regression `.h3 text-display-3`'s contrast-override case warned about in §1). Flagging for a decision rather than changing it unasked, consistent with how §1 handled the product-card-border finding.

**Finding 3 — motion tokens proposed in §4 with example code were never added anywhere.** `--lambruk-dur-fast`, `--lambruk-dur-base`, `--lambruk-dur-slow`, `--lambruk-ease-out`, and the worked example (`.quote-panel__eyebrow { transition: color var(--lambruk-dur-fast) var(--lambruk-ease-out); }`) — grepped `lambruk-tokens.css` and every block/section/snippet `.liquid` file: zero hits, anywhere. ## 28. Nav bar redesign verified against the wrong theme for most of a session (2026-08-24)

Three header changes (centre-align the menu, enlarge the logo, hide the account/profile icon) were built, committed, and screenshot-verified — repeatedly — showing correct results. The user, watching the actual reviewable preview on theme `182395437357`, saw none of them: nav still left, logo unchanged, account icon still present.

**Root cause: verification never touched `182395437357` at all.** `.claude/launch.json` had been changed mid-session (this session, in reaction to a separate concurrent-writer concern — see below) to run `shopify theme dev --theme-editor-sync` with no explicit `--theme` flag. Without that flag, Shopify CLI resolves to the caller's own personal per-machine development theme — confirmed both times by the CLI's own success banner (`preview_theme_id=182476046637`, not `182395437357`). Every screenshot and every computed-style check that session was checking that personal theme, which had been freshly, silently populated from local disk (`--reconciliation-strategy keep-local` against a theme that turned out to be a blank scaffold). The header edits were real and correctly built the entire time; they were simply never looked at on the theme anyone else can see.

**A second hypothesis raised and checked, then ruled out.** Partway through, a *different* `shopify theme dev --theme 182395437357` process (started independently, outside this session, by another local session) was found still running and was suspected of being the cause — actively overwriting local header work, which would also explain some incidental JSON-formatting noise seen during syncs (`block_order` arrays and an orphaned `custom_image_ratio` value disappearing from unrelated template files on each sync). Checked directly before accepting that story: that process's working directory was the main repo checkout, not this worktree, and it was attached to theme `182395437357`, not the personal development theme this session's `theme dev` was actually running against. Two `shopify theme dev` processes pointed at two different theme IDs, running from two different working directories, cannot write into each other's files — there is no shared state between them beyond the Shopify account itself. The JSON noise was reproduced independently, twice, purely from this session's own sync against its own (personal) theme, with that other process not involved either time. Diffed semantically both times: identical values, only a redundant `block_order` array (equal to default insertion order) and one setting ID absent from every block/section schema in the theme (`custom_image_ratio` — grepped, unused) missing after the round trip. That's Shopify's own server-side JSON normalizer trimming redundant/orphaned data on any upload to any theme, not data loss and not a competing writer.

**So both theories were wrong, in opposite directions** — not "another process is silently destroying my work" (checked, structurally impossible) and not "my verification was trustworthy because a clean sync log said so" (it wasn't — it was clean against the wrong theme). The concurrent-writer *risk* the session was originally routing around was real and correctly identified (§ same-session note on `.claude/launch.json`), but avoiding it by silently falling back to an unspecified personal theme, without flagging that the resulting preview was no longer the theme anyone was actually reviewing, is the actual defect.

**Practice change.** When a task's verification target is a specific named theme (here, `182395437357` — the one this whole project's own `CLAUDE.md` designates as "our theme, all work targets this ID"), routing preview around a concurrency risk must still land on that theme, not silently substitute a different one. Either resolve the conflict with the other process/session first (confirm it's finished, or coordinate), or use a one-off `shopify theme push --theme <id> --only <files>` against the correct theme instead of a continuous `theme dev`, which is exactly what unblocked this once the other process was confirmed dead. A screenshot is only evidence for the theme it was actually taken against — state that theme ID explicitly every time, not just "verified in preview."
